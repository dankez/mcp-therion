> Probably I'm just missing out a bit of syntax or namespace visibility.

> Any suggestions

Your StandardLayout is not visible, probably because therion did not read
configuration file with this layout. To load layouts in some standard file,
you
need to input this file first, then use copy. Example:

Let file colors.thcfg contains:

layout standard-colors
  color map-fg altitude
endlayout

To include this layout in your main thconfig file you write:

source my-data.th # to include data

input colors.thcfg # to include file

layout output-layout
  copy standard-colors
  ... other specific settings ...
endlayout

export map -layout outpu-layout

HTH, S.

Well, this is not yet implemented, but as far as I remember, you are not the
first one asking for these features. I think, it would not be very difficult to
implement it, but there are some technical issues, that need to be solved
first.

1. What data needs to be stored. So far I see: feature type (falut, layering,
fold axes?), srike and dip

2. Where exactly would you like to enter these data. Maps or centerline or
both? 

If it is a centerline - then these data would be aattributes of the station -
which position needs to be measured first. If it is map, then these data would
be attributes of a point, that is positioned in the map (=> it's 3rd coordinate
can not be given exactly).

3. How to plot these data. Are there any standard symbols for these types of
measurements, that can be used in the map? In the 3D: how to construct these
planes? Each measurement will be single small plane? Have you already seen some
3D models like this, that could be used as a template? Some time ago I have
tried something similar, but it was not very successful - my 3D model was a
mess of planes, in which it was very difficult to see what is what.

>     \color[0 0 0]{\size[26]\the\cavename}\color[0 0 0]\vskip1cm
>   \fi
>   \ifscalebar\scalebar\vskip1cm\fi

>       {\size[12]\the\comment} \par\medskip
>     \fi
>     \everypar{\hangindent=2em\hangafter=1}
>     \edef\tmp{\the\cavelength} \ifx\tmp\empty \else
>       {\size[12]\si\the\cavelengthtitle: \ss\the\cavelength\par}
>     \fi
>     \edef\tmp{\the\cavedepth} \ifx\tmp\empty \else
>       {\size[12]\si\the\cavedepthtitle: \ss\the\cavedepth\par}
>     \fi
>     \edef\tmp{\the\exploteam} \ifx\tmp\empty \else
>       {\size[12]\si\the\explotitle:
> \ss\the\exploteam\quad\si\the\explodate\par}
>     \fi
>     \edef\tmp{\the\topoteam} \ifx\tmp\empty \else
>       {\size[12]\si\the\topotitle: \ss\the\topoteam\quad\si\the\topodate\par}
>     \fi
>     \edef\tmp{\the\cartoteam} \ifx\tmp\empty \else
>       {\size[12]\si\the\cartotitle:
> \ss\the\cartoteam\quad\si\the\cartodate\par}
>     \fi
>     \edef\tmp{\the\copyrights} \ifx\tmp\empty \else
>       {\size[12]\ss\the\copyrights\par}
>     \fi
>   }
>   \formattedlegend
> }
> endcode
>
> endlayout
>
> export map -layout mylegend
>
> As you can see \size[12] is macro for setting font size. You may change font
> sizes for all items as you need.

I am not sure, I understand 100% what you are asking for, but I will try. In the
elevation projection, the facing angle parameter is part of projection
definition. 

So if you would like to have projected elevation scrap drawn when you are facing
West (270 deg), you need to specify this not only in export command, but also in
scraps. Example:

scrap xxx -proj [elevation 270]

If only elevation is used, than 0 direction is assumed. This is probably the
source of your problems. If I am wrong, please let me know.

According to Wikipedia (http://en.wikipedia.org/wiki/Magnetic_declination)

Declination converts between true and magnetic bearings: True Bearing equals
Magnetic Bearing plus Magnetic Declination. (See
http://www.ngdc.noaa.gov/seg/geomag/faqgeom.shtml#q5d).

In therion - declination is implemented this way (to avoid confusion), while in
survex:

(true bearing) = ((bearing)-(declination zero err))

Thanks for pointing out, we will mention this difference in thbook.

code metapost
def l_section (expr P)(text txt) =
  T:=identity;
  path Q; Q = punked P;
  pickup PenC;
  for t = 0 upto length P - 1:
    pair zz[];
    zz1 := point t of P;
    zz2 := point t+1 of P;
    zz3 := postcontrol t of P;
    zz4 := precontrol t+1 of P;
    if (length(zz3-1/3[zz1,zz2]) > 0.1pt) or
       (length(zz4-2/3[zz1,zz2]) > 0.1pt):
      zz5 = whatever[zz1,zz2];
      (zz3-zz5) = whatever * (zz1-zz2) rotated 90;
      draw zz1--zz5;
      zz6 = whatever[zz1,zz2];
      (zz4-zz6) = whatever * (zz1-zz2) rotated 90;
      draw zz2--zz6;
    else:
      draw zz1--zz2;
    fi;
  endfor;
  for pnt=txt:
    if pnt=-1:
    else:
      T:=identity rotated angle(thdir(Q,pnt)) shifted (point pnt of Q);
      pickup PenC;

      if known ATTR_label:

      fi;
    fi;
    exitif pnt=-1;
  endfor;
enddef;

Yes, that is intended behaviour. You sometimes need to evaluate
numerical attibutes.

Try the following:

     if known ATTR_label:
       old_lo := labeloffset;
       labeloffset := 2 mm;
       push_label_fill_color(0.7,0.7,0.7);
       p_label.bot(if numeric ATTR_label: decimal ATTR_label else:
ATTR_label fi, (point pnt of Q), angle(thdir(Q,pnt)), 8);
       labeloffset := old_lo;
       pop_label_fill_color;
     fi;

The conversion of numeric to string argument is "decimal ATTR_label"

The example also shows how to change alignment, offset and rotation of
the label.

Unfortunately the rotation (currently) does not work for circled
labels (type 5 in your example) so i used type 8 for a label with
coloured background.
