>Is there a method to represent an area of water that is temporary?

 

For water flow points and lines there are subtypes like

permanent (default), conjectural, intermittent, paleo;  (these don't all
apply to each entity - see the therion book)

 

There are summer, winter subtypes for air draught points.

 

 I don't think this was quite what you are asking, however.

 

I would tend to draw the passage dry and label it "floods regularly" or draw
it wet and label it "often dry"

Hi!

The syntax for the symbol-assign with subtypes is using a colon:
symbol-assign line wall:blocks PINEE
yet, note that this is a therion command and not a metapost command. 
Therefore it should not be inside the code metapost section (though it 
works!?).

On the other hand the "let" is a metapost command, and the line has to 
be terminated by a semicolon, or you get metapost errors.

regards,
Georg.

Ps.: This is the redefinition of line wall:blocks, I did:
def l_wall_blocks_AUT (expr P) =

  T:=identity;
  pickup PenC;
  laenge := arclength P;

  path block;
  path old_block;
 
  cur := 0;
  t:= arctime cur of P;
 
  % draw first block
  old_block := ( 
(.7u,-.35u)--(.85u,0.01u)--(.4u,.5u)--(.1u,.3u)--(-.0u,-.0u) );
  block_width := (xpart urcorner old_block - xpart ulcorner old_block);
  old_block:=old_block rotated angle( thdir(P,0) ) shifted point t of P;
  thclean (old_block--cycle);
  thdraw old_block;
 
 
  cur := cur + block_width/2;
  t:= arctime cur of P;
  forever:
    % generate random block
    block := punked ( ( 
(.8u,-.35u)--(.85u,0.01u)--(.6u,.4u)--(.1u,.1u)--(-.0u,-.3u) )
          randomized (0.3u) )
           scaled (uniformdeviate(0.3)+.65)
          rotated (uniformdeviate(45)-15);
    % check width of block
    block_width := (xpart urcorner block - xpart ulcorner block);
   
    exitif cur > (laenge- 3.5*block_width/2);
    % find next position where the block fits in without intersecting 
the previous one
    forever:   
      exitif xpart ( ((block--cycle) rotated angle(direction t of P) 
shifted point t of P) intersectiontimes old_block) < 0;
      cur:=cur+0.01u;
      t:= arctime cur of P;
      exitif cur > (laenge- 3.5*block_width/2);
    endfor;
    exitif cur > (laenge- 3.5*block_width/2);
   
    old_block:= block rotated angle(direction t of P) shifted point t of P;
    thclean (old_block--cycle);
    thdraw old_block;
   
   
    cur := cur + block_width/2;
    t:= arctime cur of P;
  endfor;
 
    % generate last block
    t:= arctime laenge-eps of P;
    block := (( 
(-.15u,-.35u)--(.0u,.0u)--(-.45u,.5u)--(-.75u,.3u)--(-.85u,-.0u)) );
    block_width := (xpart urcorner block - xpart ulcorner block);
    % scale last block to fit in the remaining gap
    scale_factor:=(laenge-cur)/block_width;
    forever:
      exitif xpart ( ( (block) rotated angle (direction t of P) scaled 
scale_factor shifted (point t of P) ) intersectiontimes old_block) < 0;
      scale_factor:=scale_factor-0.001;
    endfor;
   
    thclean (block--cycle) rotated angle (direction t of P) scaled 
scale_factor shifted (point t of P);
    thdraw (block) rotated angle (direction t of P) scaled scale_factor 
shifted (point t of P);
   
enddef;

Hi

I have had a long standing (at least since version 0.5.1) difficulty with
point label text alignment.

(Currently using 5.2.7)

 

It seems that if rotate = 0 and the alignment of the scrap in the map editor
matches (more or less) the alignment of the scrap in pdf outputs, then
commands such as  -align right or -align tl are honoured.

 

If however rotate = 70 (for example) or the scrap alignment in the map
editor is significantly different to the alignment of the scrap in the pdf
outputs then the -align parameters are incorrectly (in my view) applied.

 

The effect of this is to require the user to align scraps and xvi files to
match the finished pdf drawing output if text alignment is to be readily
controllable.  It also makes it nearly impossible to produce a scrap that
generates nice labels where it is desired to produce sets of pdf outputs
with various orientations.

 

In the attachment I have put together a dataset that starts to demonstrate
characteristics of the problem.

I have superposed survey station points and point labels so that the
alignment can be observed - a clear pattern is observable.

You can see that the alignment is based on the orientation in the map
editor, not the pdf output.

I have added some text that has orientation and applied some distortion to
the scrap by misaligning the survey stations, so you can see (another
reason)  why 'orientation' of point labels is not a good idea - scrap
distortions misalign the text a little. 

 

While it may seem trivial in this example, on a real map with labels
(perhaps at the end of arrows) it tends to make a real mess that can only be
resolved by iteration and can not usually be resolved if two or more
distinct 'rotations' are required without changing all the point labels
positions.  Not a feasible proposition.

 

Has anyone else noticed or had difficulty with this behaviour?

Is it likely that it can be altered?

 

Regards

Bruce
