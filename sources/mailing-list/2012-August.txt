No real answer, but you can equate two fixed stations, but you will need to specify error values for one or both of them.  I have done it before with coordinates in the same cs.  It should work for differing cs (I have done this in different circumstances), but of course not for an arbitrary coordinate system.  There are some interesting hacks needed in some circumstances, see http://article.gmane.org/gmane.comp.gis.therion/2909/match=loop+fix

Stacho indicated he would look at correcting some of the issues raised, perhaps why the next update is taking so long :-)

 

>From the therion book…

 

fix <station> [<x> <y> <z> [<std x> <std y> <std z>]] ◃ fix station coordinates (with specified errors—only the units transformation, not calibration, is applied to them).

 

And on transforming the plt coordinates, the calibrate option of the import command on page 33 of The Therion Book seems to suggest a way forward.  I have never used ‘import’ so cannot speak from experience.

Your suggestion of using the calibrate option with the import command did
the trick! The origin of the coordinate reference system in the PLT file
was set to one of the entrances. My calibrate command set 0 0 0 in the
input to the northing, easting, and elevation for that point, i.e. import
test.plt -calibrate [0 0 0 363315 3837128 368]. I am now able to use the
survey with the surface I've created for that area and have it tie in with
my survey.

I've commented out all of the "cs" commands in the project, as I haven't
fiddled with setting the error values for one of the stations, as suggested
by Bruce. Exported maps will at least have the correct X and Y pairs, I'll
simply have to go in after the fact and specify the specific reference
system. Thanks again for the all of the help.

This is a trivial matter, but may be worth some discussion and perhaps
adjusting Therions behaviour sometime.

 

I have been moving 'data nosurvey' entries from the main survey centreline
into their own centrelines, so that, presumably (when I learn to use sql)
users will be able to interrogate the database and uniquely identify each
unsurveyed connection, when it was made and who 'explored' it.  (The
metadata gets distributed across the whole centreline if these are all put
in the same centreline).

 

The relevant data fields would seem to be 'explo-date' and 'explo-team' and
'date' would seem to be irrelevant, as 'date' is the survey date, and these
short passages have by definition not been surveyed.

 

If however, the overall survey has a coordinate system set, and the
particular centreline has a 'data <xxx>' block set as well, then Therion
will helpfully display a warning message;

 

"warning -- unable to determine magnetic declination for undated surveys"

 

It would seem to me that 'data nosurvey' is a special case that should not
trigger this warning. 

 

An example of how I am entering these in my overall cave survey file below.

 

Regards

Bruce

 

 

  #Unsurveyed Connections

  #==================   

centreline

  explo-date 2011.05.28 

  explo-team "This Caver" 

  explo-team "That Caver"

  explo-team "Bruce Mutton"

  #date 2011.05.28 #date needed to suppress 'undated survey declination'
error

  data nosurvey from to

  jg8.10 at jg ij3.44 at ij     #unsurveyed connection Train to Carpe Diem

  ig2.60 at ig IK10.21 at ik    #unsurveyed connection What Sump Lucky Cowboy

endcentreline

  

centreline

  explo-date 2012.03.24   

  explo-team "This Caver" 

  explo-team "That Caver"

  #date 2012.03.24 #date needed to suppress 'undated survey declination'
error  

  data nosurvey from to

  kb51.33 at kb2 ka50.4 at ka2  #unsurveyed connection in KA-KB-Conscious

endcentreline
